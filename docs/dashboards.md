# 대시보드 안내

이 장비의 웹 화면은 manager 대시보드 하나입니다. 서비스를 붙이면 서비스마다 자기
대시보드를 둘 수 있고, 그 대시보드는 manager 의 로그인 세션을 그대로 받아 씁니다.
이 문서는 manager 의 화면이 무엇을 보여 주고 무엇을 바꿀 수 있는지, 그리고 어느
API 를 부르는지, 서비스 대시보드가 지킬 공통점을 정리합니다.

| 대시보드 | 주소 | 백엔드 (pm2 앱 · 내부 포트) | API 위치 |
|---|---|---|---|
| manager | `/manager` | `manager` · 28084 | `/manager/api` |

포트 번호의 뜻과 바꾸는 법은 [ports.md](ports.md) 에, 서비스가 무엇을 하는지는
[services.md](services.md) 에 있습니다.

## 1. 로그인과 세션

### 한 번 로그인하면 모든 대시보드에 들어갑니다

manager 가 로그인에 성공하면 `manager_session` 쿠키를 `Path=/` 로 발급합니다.
이 쿠키는 HMAC 으로 서명된 토큰이고, 서명 키는 `services/.session-secret`
파일입니다. manager 가 처음 뜰 때 이 파일이 없으면 만들어 둡니다(권한 600).
서비스 대시보드는 같은 파일을 읽어 그 쿠키를 검증만 합니다. 서비스 대시보드는 계정을
따로 두지 않습니다.

| 상황 | 동작 |
|---|---|
| 세션 없이 서비스 대시보드 페이지를 열었다 | `/manager/login?next=<원래 주소>` 로 302. 로그인하면 원래 페이지로 돌아갑니다 |
| 세션 없이 서비스 대시보드 API 를 불렀다 | `401` 과 `loginUrl`. 화면은 폴링 중에 401 을 받으면 로그인으로 보냅니다 |
| 토큰이 만료됐다 | 요청마다 `exp` 를 확인해 거부합니다. 기본 유효 시간은 120분(`config.json` 의 `sessionTtlMinutes`)입니다 |
| `.session-secret` 을 읽지 못했다 | 서비스 대시보드는 모든 접근을 거부합니다. manager 는 임시 키로 뜨지만 재시작하면 세션이 사라지고 다른 대시보드가 쿠키를 검증하지 못합니다 |

`?next=` 는 같은 오리진의 절대 경로(`/` 로 시작하고 `//` 가 아닌 것)만 받습니다.
열린 리다이렉트를 막기 위해서입니다.

### 계정 — 이메일과 승인

manager 계정은 MariaDB `manager` 스키마의 `administrator` 테이블에 있습니다.
아이디는 이메일만 받습니다. 등록되지 않은 이메일로 로그인하면 비밀번호 확인
칸이 한 번 더 열리고, 확인을 마치면 **승인 요청**이 만들어집니다. 방금 넣은
비밀번호가 그 계정의 비밀번호로 저장되며, 관리자가 승인해야 로그인할 수 있습니다.
승인 대기 중에 다른 비밀번호로 로그인하면 확인을 거쳐 비밀번호를 다시 설정합니다.

같은 IP 에서 5분 안에 5번 틀리면 잠깁니다. 잠금은 첫 실패 시각부터 5분 뒤에
저절로 풀리고, 화면은 남은 초를 셉니다. 사람이 풀 방법은 따로 없고
`pm2 restart manager` 를 하면 모든 잠금이 함께 풀립니다. 처음 보는 이메일로 새
승인 요청을 만든 것도 실패 횟수에 들어갑니다(테이블에 요청 행이 무한히 쌓이는
것을 막기 위해서).

### 관리자 콘솔 — 별도의 자격

로그인 화면 오른쪽 위의 작은 설정(톱니) 단추가 **관리자 콘솔**로 가는 입구입니다.
콘솔은 DB 계정이 아니라 `config.json` 의 `superAdmin` 고정 계정으로 들어가고,
쿠키도 따로(`manager_admin`, `Path=/manager`, 기본 30분) 씁니다. 비밀번호가 설정돼
있지 않으면(`superAdmin.passwordHash` 와 `password` 가 둘 다 비면) 콘솔은 열리지
않습니다. 같은 IP 에서 10분 안에 5번 틀리면 잠깁니다.

두 토큰은 서로를 대신하지 못합니다. 콘솔 토큰에는 `s: "super"` 표식이 붙어
있어서 manager 는 그것을 일반 세션으로 받지 않습니다.

### 민감한 동작 앞의 비밀번호 재확인

세션만으로는 "지금 화면 앞에 있는 사람이 그 사람인가" 를 가릴 수 없으므로, 되돌리기
어려운 동작 몇 가지는 로그인 비밀번호를 한 번 더 받습니다. 서비스는 비밀번호를
직접 판단하지 않고, 사용자의 쿠키를 그대로 실어 manager 의
`POST /manager/api/verify-password` 에 묻습니다. 실패는 로그인과 같은 IP 잠금
통에 들어갑니다. 서비스 대시보드는 이 경로를 불러 같은 확인을 받을 수 있습니다.

## 2. manager 대시보드 (`/manager`)

화면 위쪽 막대(TopBar)는 모든 화면에서 같습니다. 왼쪽 제목을 누르면 대시보드로
돌아오고, 오른쪽은 **자원 · 점검 · 포트 | (화면 고유 조작) | 구축 | 서비스 추가 · 문서** 순서이고 그 뒤에
로그인한 사람과 로그아웃 단추가 있습니다. 자원·점검·포트는 서비스가 아니라 장비 자체를 보는
화면이라 맨 앞에 두었고, 화면 고유 조작은 Dashboard 의 자동 갱신 스위치와 새로고침입니다.

| 경로 | 화면 | 들어가는 자격 |
|---|---|---|
| `/manager/login` | 로그인 | 없음 |
| `/manager/dashboard` | 서비스 상태 | 일반 세션 |
| `/manager/resources` | 장비 자원 (CPU · RAM · 저장소 · 네트워크) | 일반 세션 |
| `/manager/checks` | 점검 — 설치본이 저장소 선언과 같은가 | 일반 세션 |
| `/manager/view/<이름>` | 서비스 대시보드 담아 보기 | 일반 세션 |
| `/manager/setup` | 구축 마법사 | 일반 세션 **또는** 관리자 콘솔 세션 |
| `/manager/port-map` | 포트 지도 | 일반 세션 |
| `/manager/docs` | 문서 · 설치 가이드 PDF · 변경 이력 | 일반 세션 |
| `/manager/add-service` | 서비스 추가 마법사 | 일반 세션 (만들기는 `admin` 권한만) |
| `/manager/admin` | 관리자 콘솔 | 관리자 콘솔 세션 |

### 로그인

이메일과 비밀번호를 받습니다. 제목 아래에 **어느 장비인지**(호스트 이름과 IP 의
마지막 옥텟)를 띄웁니다. 장비가 여러 대일 때 헷갈리지 않게 하려는 것이고, 로그인
전에 부르는 `GET /api/host` 는 그 이상을 드러내지 않습니다. HTTP 로 접속하면
자격 증명이 평문으로 간다는 경고를 띄웁니다.

API: `POST /api/login`, `POST /api/logout`, `GET /api/me`, `GET /api/host`

### Dashboard — 서비스 상태

5초마다 저절로 새로 고칩니다(위 막대의 스위치로 끌 수 있습니다).

- **요약 카드 넷** — 전체 서비스 수(nginx 라우트 수와 PM2 앱 수), 정상, 비정상(중단·주의),
  Nginx 실행 여부와 버전.
- **장비 자원 카드 넷** — CPU · RAM · Storage · Network 한 줄 요약. CPU·RAM·Network 는 최근
  10분 꺾은선이 붙고, Storage 는 **가장 찬 디스크 하나**의 사용률 막대입니다(평균을 내면 가득 찬
  디스크가 가려집니다). 사용률 75% 부터 노란색, 90% 부터 빨간색입니다. 오른쪽 위 **자세히**
  가 아래 Resources 화면으로 갑니다. 서비스 상태와 따로 읽으므로 자원 측정이 실패해도 서비스
  표는 그대로 나옵니다(카드만 빠집니다).
- **Nginx 카드** — systemd 상태, 버전, PID, 가동 시간, `server_name`, HTTP/HTTPS 포트,
  mTLS(`ssl_verify_client`) 사용 여부.
- **TLS 인증서 카드** — 파일이 아니라 nginx 에 실제로 TLS 접속해서 받은 인증서를
  보여 줍니다. 종류(Let's Encrypt · 사설 CA · 시험용), 이름, 발급자, 만료일과 남은 날,
  `certbot.timer` 상태, 도메인의 A 레코드가 지금 이 서버를 가리키는지. 사설 CA 이거나
  자동 갱신이 꺼져 있거나 만료가 가깝거나 A 레코드가 어긋나면 무엇을 해야 하는지
  문장으로 적어 줍니다. 갱신은 됐는데 nginx 가 reload 되지 않은 상태도 여기서 드러납니다.
- **서비스 표** — `nginx-conf/*.ini` 와 `pm2-conf/*.ini` 를 합친 목록입니다.
  **Default**(이 저장소에 든 manager)와 **Plugged-in**(자기 저장소를 가진 plug-in)
  두 묶음으로 나뉩니다. manager 자신은 올리지 않습니다 — 이 화면이 보이면 manager 는
  떠 있는 것이라 줄이 알려 주는 것이 없고, 개수 집계에도 들어가지 않습니다. 한 폴더가 둘 이상을 선언하면(예: 본체와 대시보드를 함께 선언하는 폴더)
  폴더 머리글 아래에 묶어 보이되, 헬스는 합치지 않고 줄마다 따로 봅니다. 열은 상태,
  location, 대상(host:port), PM2 상태, 응답 시간입니다. 행을 펼치면 등록 위치,
  WebSocket 사용 여부, HTTP 상태, 마지막 확인 시각, PM2 가동 시간·재시작 횟수와
  `/health` 응답 본문이 나옵니다. 줄마다 **다시 확인** 단추가 있습니다.
- **대시보드 단추** — 자체 대시보드를 선언한 서비스에만 나옵니다. 주소는 nginx
  `location` 과 대시보드 경로(`nginx-conf` 의 `dashboard_path` 또는 `pm2-conf` 의
  `[env] DASHBOARD_PATH`)를 합쳐 만듭니다. Default 서비스는 manager 안(`/view/<이름>`)에서,
  plug-in 은 새 탭에서 엽니다.

상태 판정(정상·주의·중단·알 수 없음)의 기준은 [guide/contracts.md](guide/contracts.md)
의 `/health` 규약입니다.

API: `GET /api/overview`(모든 서비스의 헬스·pm2·nginx·인증서를 한 번에),
`GET /api/services/:name/health`(한 줄 다시 확인)

### Resources — 장비 자원

Dashboard 의 자원 카드가 가리키는 상세 화면입니다. 5초마다 저절로 새로 고칩니다.

- **CPU** — 전체 사용률, 최근 10분 그래프, load average(1·5·15분), 코어별 막대.
- **RAM** — 사용률과 그래프, 스왑, 사용 가능·캐시. 사용률은 (전체 − `MemAvailable`) 입니다.
  캐시는 커널이 필요할 때 되돌려 주는 메모리라 '사용 중' 에 넣지 않습니다.
- **Storage** — 마운트별 사용량·남은 용량. `tmpfs`·`overlay`·`squashfs` 같은 가상 파일시스템과
  같은 장치의 중복 마운트는 뺍니다.
- **Network** — 수신·송신 전송률과 그래프, 인터페이스별 링크 상태·속도·전송률·오류 수.
  `lo` 와 `veth*`·`docker*`·`br-*` 같은 가상 장치는 합계를 부풀리므로 뺍니다.
- **서비스별 사용량** — pm2 앱(`pm2 jlist`)과 systemd 유닛(`nginx` · `mariadb`)을 한 표로, 메모리 큰 순으로 보여 줍니다. 설치되지 않은 유닛은
  조용히 빠집니다. CPU 는 코어 하나를 100% 로 본 값(`top` 과 같은 기준)입니다. systemd 유닛은
  `systemctl show` 의 `MemoryCurrent`·`CPUUsageNSec`(자식 프로세스 포함)를 읽고, CPU 는 10초
  간격의 차이로 재서 처음 10초는 비어 있습니다. 그 유닛에 cgroup 회계가 꺼져 있으면 `—` 입니다.

수치는 manager 안의 sampler 가 5초마다 `/proc` 에서 재 둔 것입니다(CPU·네트워크는 누적
카운터라 두 시점의 차이로만 비율이 나옵니다). 여러 사람이 열어도 `/proc` 읽기 횟수는
늘지 않습니다. 기록은 메모리에만 있어 **manager 를 재기동하면 비워집니다.** 리눅스 전용입니다.

API: `GET /api/metrics`(현재값 + 최근 120개 기록 + pm2 앱별 사용량)

### Checks — 설치본이 선언과 같은가

SSH 가 막힌 현장에서 터미널의 `./check-all.sh` 를 대신하는 화면입니다. 열면 줄마다 **순서대로**
점검하고(한 줄씩 — nginx 가 맨 마지막), 줄마다 상태·상세·반영 명령을 보여 줍니다.

| 상태 | 뜻 |
|---|---|
| 정상 | 선언과 같습니다 |
| 어긋남 | 한 뒤에 어긋났거나 필요한 것이 없습니다 |
| 아직 안 함 | 아직 반영하지 않았습니다 (`pending`) |
| 시간 초과 | 줄당 120초 안에 끝나지 않았습니다 |
| 선택 · 안 함 | 안 써도 되는 기능이고 아직 안 했습니다. 어긋남으로 세지 않습니다 |
| 읽지 못함 | 점검 결과를 읽지 못했습니다. 어긋남으로 세지 않으니 직접 돌려 보세요 |
| 실행 실패 | 화면이 그 줄을 돌리지 못했습니다(프록시 시간 제한 등). 나머지 줄은 계속 점검합니다 |

- **점검은 아무것도 바꾸지 않습니다.** 어긋난 줄에는 터미널에서 돌릴 **반영 명령**이 복사용 글자로
  나옵니다. 거기에 더해, 마법사 단계에 이어진 줄에는 **자동으로 반영** 단추가 있습니다(아래).

- **판정은 스크립트가 냅니다.** 화면은 `check-all.sh` 의 두 모드를 읽어 보여 줄 뿐이라 터미널과
  화면이 갈라질 수 없습니다: `--list-json`(줄 번호·이름)과 `--one N --json`(N 번 줄 하나의 결과).
  화면은 **번호만** 서버에 보내고 명령은 보내지 않으므로, 스크립트 표에 없는 명령은 돌릴 수 없습니다.
- 줄 번호는 스크립트 안의 `ROWS` 순서입니다. 점검 줄을 더하거나 빼도 화면은 고칠 필요가 없습니다.
- 터미널에서도 `./check-all.sh --one 3` 처럼 한 줄만 볼 수 있습니다.
- 같은 줄을 동시에 두 번 돌리지 않고 이미 도는 점검의 결과를 같이 받습니다.

#### 자동으로 반영

어긋남·아직 안 함인 줄에서 단추를 누르면 이 명령들을 순서대로 돌린다고 **먼저 보여 주고**, `sudo` 가
필요하면 비밀번호를 받습니다. 진행 로그가 줄 아래에 흐르고, 끝나면 그 줄을 **다시 점검**합니다 — 고쳐졌는지는
반영이 아니라 점검이 정합니다. 반영 중에는 중단할 수 있고, 반영하고도 어긋나 있으면 로그가 그대로 남습니다.

- **새 실행 경로를 만들지 않았습니다.** 점검 줄은 `check-all.sh` 의 표가 가리키는 **구축 마법사 단계 하나**에
  이어지고, 돌리는 것은 그 단계의 자동 실행 표(`setup.js` 의 `AUTO`)에 박힌 명령뿐입니다. 화면이 보내는 것은
  점검 번호와 `sudo` 비밀번호뿐입니다. 비밀번호는 마법사와 같은 방식(메모리에만, askpass 소켓)으로 전달되고
  로그에서 가려집니다. 줄 ↔ 단계 연결은 `check-all.sh` 의 줄 옆(다섯째 칸)에 적습니다.
- **HTTPS 로 온 요청만** 받습니다. 평문 HTTP 로 온 요청은 서버가 `403 https_required` 로 거부합니다(화면의 경고에
  맡기지 않습니다). nginx 를 거치지 않고 `127.0.0.1:포트` 로 SSH 터널을 타고 직접 붙은 경우는 예외입니다.
  구축 중 `--expose-http` 로 마법사를 평문으로 쓰는 흐름은 마법사 라우트라 그대로 두었습니다.
- **admin 역할만** 반영할 수 있습니다(서비스 추가와 같은 기준). 그 밖의 계정은 점검만 봅니다. 요청 본문은
  JSON 만 받습니다.
- **일부러 반영을 내밀지 않는 줄**: pm2 줄(`pm2 save` 가 어긋난 설정을 굳힙니다), manager 세 줄(manager 를
  재시작하면 이 화면이 끊깁니다). 사람이 정해야 하는 단계는 단추 대신 이유를 보여 줍니다.
- **점검 전용 반영과 게이트.** 구축 마법사의 단계로는 그 줄을 고치는 일을 나타낼 수 없을 때
  쓰는 자리가 `checks.js` 의 `CHECK_ONLY` 입니다. 이 판에서는 비어 있습니다. 서비스를 붙였는데 점검 줄이
  어긋나는 흔한 이유가 "`dist/` 가 `src/` 보다 오래됨" 이라면 빌드와 재시작을 여기에 둡니다. 재시작이 깨진
  설정을 서비스에 먹일 수 있는 서비스에는 **게이트**를 달아, 반영 직전에 서버가 그 서비스의 설정 점검만 따로
  돌려 온전하지 않으면 `409 precondition_failed` 로 시작하지 않게 합니다. 점검을 읽지 못한 경우도 통과시키지
  않습니다.
- **nginx 줄**은 nginx 를 다시 읽혀 연결이 잠깐 끊길 수 있다고 미리 알립니다.
- 반영 작업은 **한 번에 하나**입니다. 마법사에서 돌고 있는 자동 실행과 같은 자리를 쓰므로 겹치면 `409 busy` 입니다.

API: `GET /api/checks`(줄 목록과 줄마다 반영 설명), `POST /api/checks/:id/run`(한 줄 점검 — 프로세스를 띄우므로 POST),
`POST /api/checks/:id/apply`(반영 시작 · 본문 `{sudoPassword}`), `GET /api/checks/:id/apply?from=N`(진행 읽기),
`POST /api/checks/:id/apply/cancel`(중단)

### ServiceView — 서비스 대시보드 담아 보기

`/manager/view/<이름>` 은 Default 서비스의 대시보드를 manager 위 막대 아래에
iframe 으로 담습니다. 같은 오리진이고 같은 세션을 쓰므로 그대로 실립니다. 위
막대의 **새 탭** 단추로 그 대시보드만 따로 열 수 있습니다. plug-in 이면 담지 않고
새 탭 링크만 보여 주고, 대시보드를 선언하지 않은 서비스면 그렇다고 알려 줍니다.
주소창은 `/view/<이름>` 에 머물기 때문에 새로 고치면 그 대시보드의 첫 화면으로
돌아갑니다.

API: `GET /api/services/:name`(헬스 검사 없이 선언값만 — `dashboardUrl` 을 얻는 용도)

### Setup — 구축 마법사

빈 장비를 처음부터 세우는 순서를 단계별로 보여 주고, 각 단계의 점검 스크립트를
대신 돌려 결과를 표시합니다. 단계는 다음 9개입니다(필수 5, 선택 4).

사이트 값 → pm2 → MariaDB 스키마 → TLS 결정 → nginx 라우트 →
(선택, 공인 인증서) 발급 → nginx 반영 → 갱신 → DNS 점검

- 단계마다 **왜 필요한가**, 터미널에서 **실행할 것**, 점검 결과를 보여 줍니다.
  마법사는 sudo 를 부르지 않습니다. 사람이 명령을 돌리고 **했습니다 — 점검하기**를
  누르는 방식입니다.
- 통과 여부는 점검 스크립트의 `--json` 출력으로만 정합니다. 앞 단계가 통과하지
  않았으면 경고를 띄우지만 점검은 돌려 볼 수 있습니다.
- 장비마다 다른 값을 받는 단계는 폼을 보여 주고, 값을 그 서비스의 `settings.ini`
  에 적습니다. **적기만 하고 반영하지 않습니다.** 설치된 값과 다르면 "아직 반영되지
  않았습니다" 와 반영 명령을 보여 줍니다.
- 기계가 확인할 수 없는 것(인터폰 계정이 있는가, 공유기 포워딩을 열었는가)은
  **사람의 확인**을 기록합니다. 누른 사람과 시각이 남고, 확인 대상(예: 포워딩 포트
  목록)이 나중에 바뀌면 다시 묻습니다. 확인은 통과로 바꾸는 것이 아니라 기록입니다.

빈 장비에는 아직 MariaDB 가 없어 일반 로그인을 할 수 없으므로, 마법사만은 관리자
콘솔 세션으로도 들어갑니다. 이때 화면 위에 그 사실을 띄우고, 기록에는
`console:<아이디>` 로 남습니다. 단계별 내용은 [guide/install.md](guide/install.md) 에 있습니다.

**자동 실행의 시작·중단은 admin 역할(또는 콘솔 세션)만 할 수 있습니다.** 장비를 바꾸고 `sudo` 비밀번호를
받는 동작이라 읽기 전용 계정(viewer)이 누를 일이 아닙니다. 콘솔 세션은 통과시킵니다 — 빈 장비의 첫 구축은
콘솔로만 들어오고 그 세션에는 role 이 없는데, 콘솔 `superAdmin` 은 이미 이 시스템의 최상위 자격이라 막을 이유가
없습니다. role 이 실리기 전의 옛 세션 토큰은 막히니 다시 로그인하세요. 진행 읽기(`GET`)와 점검은 그대로 일반
세션이 봅니다. **HTTPS 는 마법사에서 강제하지 않습니다** — 구축 중 `bootstrap.sh --expose-http` 로 평문으로 여는
흐름이 있고, 구축이 끝난 장비는 nginx 80 이 전부 https 로 넘겨 평문 요청이 manager 에 닿지 않기 때문입니다
(HTTPS 를 서버에서 강제하는 쪽은 운영 중 장비를 고치는 점검 화면의 반영입니다). 같은 경로의 설정 저장
(`PUT /setup/settings`)과 확인 기록은 이번에 바꾸지 않았습니다.

API: `GET /api/setup`, `POST /api/setup/check/:stepId`, `PUT /api/setup/settings/:stepId`,
`POST·DELETE /api/setup/attest/:stepId`

### PortMap — 포트 지도

공유기를 바꾸거나 포워딩을 다시 확인할 때 보는 화면입니다. 네 표로 나뉩니다.

1. 공유기 포트 포워딩 체크리스트 — 공유기에서 열어야 하는 것만
2. RTP/미디어(UDP) 대역
3. 시그널링 · 컨트롤 포트
4. 내부 HTTP 포트(nginx 라우팅) — 전부 127.0.0.1 백엔드

값은 각 서비스의 `settings.ini`(없으면 `settings-schema.json` 기본값)와
`nginx-conf/*.ini` 를 요청할 때마다 다시 읽은 것이라 문서보다 늘 최신입니다. 각 줄에
"공유기 포워딩 필요" 또는 "LAN 전용" 표시가 붙습니다. 숫자의 뜻과 바꾸는 법은
[ports.md](ports.md) 에 있습니다.

API: `GET /api/port-map`

### Docs — 문서 · 설치 가이드 · 변경 이력

세 탭입니다.

- **문서** — git 이 추적하는 `.md` 파일 전부를 디렉터리별로 묶어 보여 주고, 고르면
  Markdown 으로 그려 줍니다. 파일 이름·제목으로 거를 수 있습니다. 목록에 없는 경로는
  읽지 않으므로 커밋되지 않는 비밀·장비별 값(`settings.ini`, `secrets/`)은 애초에
  나오지 않습니다.

### AddService — 서비스 추가 마법사

새 서비스를 붙이는 두 단계를 안내합니다.

1. **기본 틀 만들기** — 이름(소문자·숫자·하이픈, 최대 40자), 내부 포트
   (28080–28099 중 비어 있는 것을 제안), 트랙(이 저장소에 커밋 / 별도 저장소
   plug-in)을 받아 `services/<이름>/` 에 고정 템플릿으로 스켈레톤을 만듭니다. 이미
   쓰이는 이름·포트는 입력하는 동안 막습니다. 이 저장소에 커밋하는 트랙이면
   `.gitignore` 에 `!services/<이름>/` 예외를 추가합니다. 이 동작만은 계정의
   role 이 `admin` 이어야 합니다(서버가 403 으로 막습니다).
2. **등록** — 실행할 명령(DB · pm2 · 확인 · nginx · 다시 확인 순서)을 복사용으로
   보여 주고, 무결성 점검(이름이 세 곳에서 같은가, `/health` 규약, nginx·pm2 선언
   충돌, `.gitignore` 예외)을 돌립니다. 명령은 마법사가 실행하지 않습니다.

절차의 배경은 [guide/rollout.md](guide/rollout.md) 에 있습니다.

API: `GET /api/wizard/scaffold/defaults`, `POST /api/wizard/scaffold`,
`GET /api/wizard/register/:name/checklist`, `POST /api/wizard/register/:name/check/:checkId`,
`GET /api/wizard/register/:name/commands`

### AdminConsole — 관리자 콘솔

`administrator` 테이블을 직접 다루는 화면입니다. 표에는 ID, 이메일, 이름, 권한
(`admin` · `viewer`), 승인, 요청 시각, 마지막 로그인, 로그인 횟수가 나옵니다.

- 승인 스위치는 바로 바뀝니다. 끄면 그 계정은 즉시 로그인할 수 없습니다.
- 관리자 추가(바로 승인 여부 선택), 이름·권한 편집, 비밀번호 변경(8자 이상), 삭제.
- 모든 변경은 `admin_audit_log` 에 남습니다.
- 위의 **구축 마법사** 단추는 빈 장비에서 마법사로 가는 유일한 길입니다. DB 가
  아직 없으면 목록이 오류를 내는 것이 정상이고, 화면이 그렇게 안내합니다.

API: `POST /api/admin/login`, `POST /api/admin/logout`, `GET /api/admin/me`,
`GET·POST /api/admin/administrators`, `PATCH·DELETE /api/admin/administrators/:id`

## 3. 서비스 대시보드의 공통점

서비스를 붙이면서 자기 대시보드를 두려면 아래를 지키는 것이 관례입니다.

- 위쪽에 탭 막대가 있습니다. manager 는 이 화면들을 iframe 안에 넣으므로 **manager 로
  돌아가는 링크는 두지 않습니다** — 누르면 iframe 안에 manager 가 다시 뜹니다.
- 서비스 본체를 systemd 가 띄운다면 대시보드는 그것과 **다른 프로세스**로 둡니다. 본체가
  죽어도 대시보드는 살아서 "떠 있지 않습니다" 를 보여 줍니다.
- **로그** 탭이 필요하면 systemd 저널을 읽기 전용으로 보여 줍니다(줄 수 · 기간 · 정규식 필터 ·
  따라가기). 유닛 이름은 코드에 고정해 셸을 거치지 않습니다(`lib/journal.js`).
- 대시보드는 sudo 를 갖지 않습니다. 설정 탭에서 값을 바꾸면 `settings.ini` 에 적기만 하고,
  반영은 사람이 합니다. 폼 정의는 각 서비스의 `settings-schema.json` 한 곳이라 구축 마법사에서
  넣어도 같습니다 ([guide/contracts.md](guide/contracts.md) 의 settings 규약).
- 화면은 5–15초 간격으로 폴링합니다.

## 4. 개발할 때

프런트를 고칠 때는 각 `web/` 에서 `npm run dev` 로 Vite 개발 서버를 띄웁니다. API 는
그 서비스의 내부 포트로 프록시됩니다.

| 대시보드 | 개발 서버 포트 |
|---|---|
| manager | 5183 |

빌드 산출물(`web/dist/`)은 커밋하지 않습니다. 빌드가 없으면 대시보드 경로가 503 을
내고 `/health` 는 정상으로 남습니다. 빌드와 반영 절차는 [guide/rollout.md](guide/rollout.md)
에 있습니다.
